# Repository Guidelines

## Project Structure & Module Organization

This repository currently contains specifications for a bank marketing CRM; application code, tests, and build configuration have not been scaffolded.

- `requirement.txt` describes the overall product requirements; it is not a Python dependency file.
- `Bank Marketing CRM — Phase 1 Spec Core Modules & POS Management.md` defines the backend scope, architecture, API, and business rules.
- `openspec/config.yaml` selects the `spec-driven` OpenSpec schema.
- `docs/` is currently empty.

The planned backend uses Python 3.12, FastAPI, and PostgreSQL 16. Follow the specified layout: `app/core/` for shared infrastructure, `app/models/` for SQLAlchemy models, `app/schemas/` for Pydantic schemas, `app/features/` for feature routers and services, `migrations/` for Alembic, and `tests/` mirroring features.

## Build, Test, and Development Commands

No runnable build or test commands exist yet. Once the specified `uv` project and tooling are scaffolded, use:

- `uv sync` — install project dependencies.
- `uv run pytest` — run the test suite against a real PostgreSQL instance.
- `uv run ruff check .` — lint Python code.
- `uv run ruff format .` — format Python code.
- `uv run alembic upgrade head` — apply database migrations.

Document the actual local server command when the application entry point exists.

## Coding Style & Naming Conventions

Use four-space Python indentation and Ruff formatting. Keep routers thin and business rules in async service functions. Services raise `DomainError` subclasses and call `flush`, leaving commit or rollback to the request session dependency. Avoid cross-feature service imports.

Use `snake_case` columns and plural `snake_case` tables. Name schemas `XCreate`, `XUpdate`, `XOut`, and `XListItem`. Use timezone-aware UTC datetimes and `Decimal` for money.

## Testing Guidelines

The specification selects pytest, pytest-asyncio, and httpx `AsyncClient`. Name test files `test_*.py`. Cover role and branch isolation, soft deletion, audit records, import errors, and POS task transitions. No numeric coverage threshold is currently defined.

## Commit & Pull Request Guidelines

There are no commits yet, so no established message convention exists. Use concise, imperative subjects, such as `Document POS transfer constraints`. PRs should describe scope, reference affected specification sections or issues, and report validation performed. Explain schema changes and review autogenerated migrations manually.

## Security & Scope

Keep secrets in environment variables and document configuration in `.env.example` when introduced. Use synthetic banking data in examples. Preserve historical business records through soft deletion. Phase 1 is backend-only and excludes Core Banking integration.
